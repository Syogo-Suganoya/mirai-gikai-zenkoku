# デプロイ手順

みらい議会＠全国地方議会を本番環境に出す手順です。構成は設計 v3 の 2.5節のとおりです。

| 用途 | サービス | 備考 |
|---|---|---|
| 公開サイト（`web/`） | Vercel | プロジェクトを2つ作る（web・admin） |
| 管理画面（`admin/`） | Vercel | |
| DB | Neon（PostgreSQL） | アプリは接続プール（`-pooler`）の URL、マイグレーションは直接接続の URL |
| ファイル（サムネイル・取り込んだ CSV） | Vercel Blob | admin のプロジェクトにストアをつなぐ。公開 URL（`*.public.blob.vercel-storage.com`）で配信する |
| AI | Google Gemini API | AI チャット・インタビューなど（ふりがなは辞書で付けるので AI を使わない） |
| CI・CD | GitHub Actions | CI は `code_check.yml`・`integration_test.yml`。CD は `deploy.yml` |

全体の流れは次のとおりです。初回は 1〜8 を順に行い、2回目以降は「9. 2回目以降のデプロイ」だけです。

| 手順 | やり方 |
|---|---|
| 1. Neon で DB を作る | 画面 |
| 2. マイグレーションを当てる | ターミナル |
| 3. 初期データを入れる | ターミナル |
| 4. 最初の管理者を作る | ターミナル |
| 5. Gemini の API キーを作る | 画面 |
| 6. Vercel にプロジェクトを2つ作り、ファイルの置き場所（Blob）をつなぎ、環境変数を入れてデプロイする | 画面 |
| 7. GitHub Actions の CD を有効にする | 画面（ファイルのコミットだけ git） |
| 8. 公開前の確認 | ブラウザ |

各サービスの画面の操作は「画面での操作」に、ボタンやメニューの名前を英語のまま書いています（2026年10月時点。名前や配置は変わることがあります）。

ターミナルが要るのは 2〜4 だけです。手元の PC に Node.js 20 と pnpm を入れ、このリポジトリを clone して `pnpm install` しておきます。

画面の操作（1・5〜7）は、すべてコマンドでもできます。まとめて「12. 付録: コマンドでの操作」に書いています。

> コマンドはリポジトリのルートで実行します。本番の接続 URL などの秘密の値はターミナルの履歴に残さないよう、`export` で一時的に入れるか、パスワード管理ツールから貼り付けてください。

---

## 1. Neon で DB を作る

### 画面での操作

1. [Neon](https://console.neon.tech/) にサインアップします（GitHub アカウントでも可）。
2. 「New Project」を押し、次のように入れて「Create」。

   | 項目 | 値 |
   |---|---|
   | Project name | 例: `mirai-gikai-zenkoku` |
   | Postgres version | 17（CI の統合テストと同じ） |
   | Region | 日本に近いところ（一覧に東京があれば東京、なければシンガポール）。6章の Vercel の Function Region と揃える |
   | Database name | 既定の `neondb` のままでよい |

3. プロジェクトの Dashboard で「Connect」を押し、接続 URL を2つ控えます。ダイアログの「Connection pooling」をオンにすると接続プールの URL、オフにすると直接接続の URL が出ます。

   | 名前 | 使う場所 | 見分け方 |
   |---|---|---|
   | 接続プールの URL | アプリ（Vercel の `DATABASE_URL`） | ホスト名に `-pooler` が付く |
   | 直接接続の URL | マイグレーション・初期データ（手元と GitHub Actions） | `-pooler` が付かない |

   アプリは接続プール越しに使うため、DB の接続で prepared statement を使わない設定にしてあります（`packages/db/src/client.ts`）。マイグレーションはプールを通すと失敗することがあるので、直接接続を使います。

4. 左のメニューの「SQL Editor」で、あとから中身を確かめられます（例: 2章のあとに `select count(*) from bills;`）。「Tables」でもテーブルを見られます。
5. プレビュー用・ステージング用の DB が要るときは、左のメニューの「Branches」→「New Branch」で本番から分けて作ります（今はプレビューのデプロイを止めているので不要。7章）。

## 2. マイグレーションを当てる

```bash
export DATABASE_URL='<Neon の直接接続 URL>'
```

```bash
pnpm --filter @mirai-gikai/db migrate
```

- `packages/db/migrations/` の SQL を順に当てます。当てたものは DB の `drizzle.__drizzle_migrations` に記録され、2回目以降は新しいものだけを当てます。
- パスワードのハッシュに使う `pgcrypto` 拡張は、マイグレーション（`0001_functions.sql`）が作ります。
- ルートの `pnpm db:migrate` は `.env` を読むので、本番には使わないでください（`.env` はローカルの DB を指しています）。
- Neon の SQL Editor に SQL を貼って当てるのはやめてください。`drizzle.__drizzle_migrations` に記録が残らず、次のマイグレーションで同じ SQL をもう一度当てようとして失敗します。
- 7章の CD を入れたあとは、ブラウザだけで当てられます（GitHub の「Actions」→「Migrate DB then Deploy」→「Run workflow」）。初回も、先に 7章を済ませればこの方法で当てられます（そのときは続けてデプロイも走ります）。

## 3. 初期データを入れる

```bash
pnpm --filter @mirai-gikai/seed seed:initial
```

（`DATABASE_URL` は 2章で入れた直接接続の URL のまま）

入るもの（設計 v3 8章）:

| データ | 件数 |
|---|---|
| タグ | 13 |
| 47都道府県議会の議会マスタ | 47 |
| 愛知県議会の会期・議案・議決結果 | 会期5・議案226（うち解説付き5）。すべて公開 |
| 46都道府県議会のダミー | 議案138（会期・会派つき）。件名に「【ダミー】」 |

- データを消すことはなく、ローカル用の管理者も作りません。
- 愛知県議会の議案が既にあると止まります（管理画面で直した公開状態や解説を上書きしないため）。どうしても入れ直すときだけ `--force` を付けます。
- ローカル開発用の `pnpm seed` は DB を空にしてから入れるので、ローカル以外の DB では動かないようにしてあります。

あとからダミーだけを入れ直すときは `pnpm --filter @mirai-gikai/seed seed:dummy`（実データのある議会には入れません）。

## 4. 最初の管理者を作る

```bash
pnpm --filter @mirai-gikai/seed admin:create <メールアドレス>
```

- 初期パスワードが1度だけ表示されます。本人に安全な方法で渡し、初回ログインで変えてもらいます。
- 2人目以降の管理者は管理画面の「アカウント」から作ります。管理者は全員同じ権限で、すべての議会・機能を扱えます。
- パスワードを忘れたときは `admin:create <メールアドレス> --reset` で初期パスワードを発行し直します（ログイン中のセッションも消えます）。

終わったら `unset DATABASE_URL` で手元の環境変数を消しておきます。

## 5. Gemini の API キーを作る（画面での操作）

1. [Google AI Studio](https://aistudio.google.com/) に、運営用の Google アカウントでログインします。
2. 左下の「Get API key」→「Create API key」で、キーを作るプロジェクト（Google Cloud のプロジェクト）を選んで作ります。これが `GOOGLE_GENERATIVE_AI_API_KEY` です。
3. 無料枠のままだと回数の制限が厳しいので、同じ画面でプロジェクトに課金（Billing）を設定します。
4. [Google Cloud コンソール](https://console.cloud.google.com/) の「お支払い」→「予算とアラート」で、月の予算とアラートのメールを設定しておきます（10章）。

## 6. Vercel にプロジェクトを2つ作る

同じ GitHub リポジトリから、web と admin の2つのプロジェクトを作ります。設定の値は 6.1 の表、環境変数は 6.2 の表を見ながら入れます。

### 6.1 プロジェクトを作る（画面での操作）

1. [Vercel](https://vercel.com/) に GitHub アカウントでログインし、右上の「Add New…」→「Project」。
2. 「Import Git Repository」で GitHub のリポジトリを選んで「Import」（一覧に出ないときは「Adjust GitHub App Permissions」で Vercel にリポジトリへのアクセスを許可します）。
3. 「Configure Project」の画面で次のように入れます。

   | 項目 | web | admin |
   |---|---|---|
   | Project Name | 例: `mirai-gikai-zenkoku-web` | 例: `mirai-gikai-zenkoku-admin` |
   | Framework Preset | Next.js | Next.js |
   | Root Directory（「Edit」で選ぶ） | `web` | `admin` |
   | Build and Output Settings | 既定のまま（pnpm と `next build` を自動で使う） | 同左 |
   | Environment Variables | 6.2 の表の値（`.env` の形の文字列を貼り付けると一度に入る） | 同左 |

4. 「Deploy」を押します。1回目のビルドはここで走ります（失敗したら環境変数を見直し、6.4 の手順で出し直します）。
5. もう一度「Add New…」→「Project」から、同じリポジトリで admin のプロジェクトを作ります。

プロジェクトを作ったら、それぞれの「Settings」で次を確かめます。

| 画面 | 項目 | 値 |
|---|---|---|
| Settings → Build and Deployment | Node.js Version | 20.x |
| Settings → Build and Deployment | Root Directory の「Include files outside of the root directory in the Build Step」 | 有効（`packages/` を使うため） |
| Settings → Functions | Function Region | Neon のリージョンに近いところ（例: Tokyo `hnd1`、Singapore `sin1`） |
| Settings → Domains | 「Add Domain」 | web に公開用（例: `gikai.example.jp`）、admin に管理用（例: `admin.gikai.example.jp`）。表示される DNS レコードをドメインの管理画面に登録する |

- `web/vercel.json`・`admin/vercel.json` で、main の Git 連携デプロイと、main 以外のプレビューを止めています（今はコミットしていない下書き。7章）。これらを入れたあとの main へのデプロイは GitHub Actions がマイグレーションのあとに行います。CD を使わず手動で出すあいだは、6.4 の「Redeploy」で出します。

### 6.2 環境変数

「Settings → Environment Variables」で、Environments を「Production」にして入れます。「Add Another」で行を足すか、`.env` の形の文字列を貼り付けると一度に入ります。秘密の値（キー・パスワード・URL に含まれる DB のパスワード）は「Sensitive」をオンにすると、あとから画面で見えなくなります。

**両方に入れるもの**

| 名前 | 値 |
|---|---|
| `DATABASE_URL` | Neon の**接続プール**の URL（`-pooler` 付き） |
| `REVALIDATE_SECRET` | ランダムな文字列（web と admin で同じ値。admin から web のキャッシュを消すときに使う） |
| `GOOGLE_GENERATIVE_AI_API_KEY` | 5章の Gemini API のキー |
| `NEXT_PUBLIC_WEB_URL` | 公開サイトの URL（例: `https://gikai.example.jp`） |
| `ADMIN_URL` | 管理画面の URL（例: `https://admin.gikai.example.jp`） |

**web だけ**

| 名前 | 値 | |
|---|---|---|
| `VISITOR_COOKIE_SECRET` | 32文字以上のランダムな文字列 | 必須（住民の匿名 ID の署名に使う。無いとすべてのページがエラーになる） |
| `CHAT_DAILY_USER_COST_LIMIT_USD` | 例: `0.5` | 任意（AI チャットの1人1日の上限。既定 0.5） |
| `CHAT_DAILY_TOTAL_COST_LIMIT_USD` | 例: `50` | 任意（全体の1日の上限。既定 50） |
| `CHAT_MONTHLY_TOTAL_COST_LIMIT_USD` | 例: `1000` | 任意（全体の1か月の上限。既定 1000） |
| `BASIC_AUTH_USER`・`BASIC_AUTH_PASSWORD` | | 任意。公開前に関係者だけで見るときに入れ、公開するときに消す |
| `NEXT_PUBLIC_GA_TRACKING_ID` | | 任意（Google アナリティクス） |
| `LANGFUSE_PUBLIC_KEY`・`LANGFUSE_SECRET_KEY`・`LANGFUSE_BASE_URL`・`LANGFUSE_PROMPT_LABEL` | | 任意（プロンプト管理・AI の監視） |

**admin だけ**

| 名前 | 値 | |
|---|---|---|
| `BLOB_READ_WRITE_TOKEN` | 6.3 でストアをつなぐと自動で入る（手で入れない） | 必須（無いとサムネイルや CSV の取り込みでエラー） |
| `LANGFUSE_*` | | 任意 |

ランダムな文字列は次で作れます（ターミナルを使わないなら、パスワード管理ツールの生成機能で 48 文字以上の英数字を作っても構いません）。

```bash
openssl rand -base64 48
```

環境変数を変えても、動いているデプロイには反映されません。変えたら 6.4 の手順で出し直します（`NEXT_PUBLIC_` で始まる値はビルド時に埋め込まれるので、特に忘れないようにします）。

### 6.3 ファイルの置き場所（Vercel Blob）をつなぐ（画面での操作）

管理画面で上げたサムネイル画像と、取り込んだ CSV の元ファイルを置きます。ファイルを書き込むのは admin だけで、web は公開 URL の画像を表示するだけなので、ストアは admin のプロジェクトにつなぎます。

1. Vercel のチームの画面の上のタブ「Storage」→「Create Database」（または「Create」）で「Blob」を選び、「Continue」。
2. 次のように入れて「Create」。

   | 項目 | 値 |
   |---|---|
   | Name | 例: `mirai-gikai-zenkoku-files` |
   | Region | 選べるなら、Neon・Function Region に近いところ（例: Tokyo `hnd1`） |
   | Access | Public（サムネイルを公開サイトで表示するため） |

3. 作ったストアの画面の「Connect Project」（または「Projects」タブの「Connect Project」）で admin のプロジェクトを選び、Environments は Production（ローカルからも試すなら Development も）にチェックして「Connect」。
4. admin の「Settings → Environment Variables」に `BLOB_READ_WRITE_TOKEN` が入ったことを確かめます。このトークンでストアに書き込めるので、ほかへ貼らないでください。
5. つないだだけでは動いているデプロイに反映されないので、6.4 の手順で admin を出し直します。

- 取り込んだ CSV の元ファイルも公開 URL 配下に置かれますが、ファイル名がランダムな ID なので推測はできません。CSV には公開している議案の情報しか入らない想定です。
- 保存したファイルは、ストアの画面の「Browser」で一覧・削除できます。容量と転送量は同じ画面の「Usage」（またはチームの「Usage」）で見られます。
- Vercel の Hobby プランは**非商用の利用に限られます**。Blob の無料枠（保存容量・転送量）にも上限があるので、最新の値は Vercel の料金ページで確かめてください。商用で使うときや無料枠を超えるときは Pro プランにします。
- web 側の設定は要りません（`*.public.blob.vercel-storage.com` の画像を表示してよいことは `web/next.config.ts` に書いてあります）。

### 6.4 デプロイし直す（画面での操作）

1. プロジェクトの「Deployments」を開き、いちばん上（Production）の行の右の「⋯」→「Redeploy」。
2. ダイアログの「Use existing Build Cache」はオフにして「Redeploy」（環境変数を変えたあとは必ずオフ）。
3. 「Ready」になったら、「Visit」で開けることを確かめます。
4. ドメインを付けたら、`NEXT_PUBLIC_WEB_URL`・`ADMIN_URL` がそのドメインになっているか確かめ、違えば直して出し直します。

## 7. GitHub Actions の CD を有効にする

main に入ったら、Neon にマイグレーションを当ててから Vercel の web・admin をデプロイする仕組みです（新しいコードが古いスキーマの DB で動くことを防ぐ）。

使うファイル:

| ファイル | 役割 |
|---|---|
| `.github/workflows/deploy.yml` | main への push で、マイグレーション → Deploy Hook |
| `web/vercel.json`・`admin/vercel.json` | main の Git 連携デプロイを止め、ignoreCommand を指定 |
| `scripts/vercel-ignore-build.mjs` | main 以外（プレビュー）のビルドを飛ばす |

### 画面での操作

1. **Vercel の Deploy Hook を作る:** 両方のプロジェクトで「Settings → Git」の「Deploy Hooks」に、名前（例: `github-actions`）とブランチ `main` を入れて「Create Hook」。出てきた URL を控えます（この URL を知っていれば誰でもデプロイを起こせるので、秘密として扱います）。
2. **GitHub に環境と Secrets を作る:** リポジトリの「Settings」→ 左の「Environments」→「New environment」で `production` を作ります。
   - 「Environment secrets」の「Add environment secret」で、次の3つを入れます。

     | Secret | 値 |
     |---|---|
     | `NEON_DATABASE_URL_UNPOOLED` | Neon の**直接接続**の URL |
     | `WEB_VERCEL_DEPLOY_HOOK_URL` | web の Deploy Hook の URL |
     | `ADMIN_VERCEL_DEPLOY_HOOK_URL` | admin の Deploy Hook の URL |

   - デプロイ前に人が確認したいときは、同じ画面の「Required reviewers」にチェックを入れて承認者を選び、「Save protection rules」。
   - 「Deployment branches and tags」を「Selected branches and tags」にして `main` だけを足すと、main 以外から本番に出せなくなります。
3. **ファイルを入れる:** 上の4つのファイルを見直してコミットし、main に入れます（ここだけ git の操作）。以降は main に入るたびに自動でデプロイされます。
4. **動いたか確かめる:** リポジトリの「Actions」タブで「Migrate DB then Deploy」の実行が緑になっているか見ます。承認者を付けたときは、実行の画面の「Review deployments」から承認します。
5. **手動で出し直す:** 「Actions」→ 左の「Migrate DB then Deploy」→ 右の「Run workflow」→ ブランチ `main` で「Run workflow」。

プレビューのデプロイ（PR ごと）は止めています。PR ごとの DB（Neon のブランチ）を用意すれば、`scripts/vercel-ignore-build.mjs` を直して有効にできます。

### 7.1 インタビューのトピック分析

AI インタビューの公開された回答を、AI がトピックにまとめて議案ページに表示します。追加の設定は要りません（Gemini のキーは 6.2 で入れたもの）。

- **いつ動くか:** 公開を許可した回答でインタビューが完了するたび（あとから公開に切り替えたときも）、web がその議案の分析（差分）を動かします。応答を返したあと、同じ関数の中で動きます（Next.js の `after`）。管理画面の「トピック分析」からも、議案ごと・全議案で手動で動かせます（同じく応答のあとに動く）。
- **重ならない:** 同じ議案の分析が実行中なら、後の分は飛ばします。その回答は次の分析で入ります。
- **時間の上限:** 関数の上限（`maxDuration = 300`。Vercel の Hobby の上限）を超えると途中で止まり、その版は10分後に失敗の扱いになって、次から実行し直せます。意見が増えて全体のやり直しなどが収まらなくなったら、本家のように Vercel の外（GitHub Actions など）で動かす形に移します。
- **インタビューを出す:** 管理画面の議会設定で「AIインタビュー」をオンにし、議案ごとにインタビューの設定を作って公開します。ダミーデータが残っている議会では出せません（架空の議案に住民の意見を集めないため）。
- **動いたか確かめる:** 公開を許可してインタビューを1回完了したあと、議案ページの「トピック」に表示されるか見ます。出ないときは Vercel の web の「Logs」で `[topic-analysis]` の行を探します。

## 8. 公開前の確認

| 確認すること | 見るところ |
|---|---|
| トップに日本地図が出て、愛知県が「議案あり」の色、ほかがダミーの色 | `/` |
| 愛知県議会のトップ・議案一覧・解説付きの議案（5件）・件名のみの議案が開ける | `/aichi-pref` など |
| ダミーの議会に「表示確認用のダミーです」の帯が出る | `/tokyo-pref` など |
| ダミーの議会は `noindex`、愛知県は `index` | ページのソースの `<meta name="robots">` |
| サイトマップに愛知県の議案があり、ダミーが無い | `/sitemap.xml` |
| robots.txt にサイトマップの URL が出る | `/robots.txt` |
| AI チャットが答える（Gemini のキーが効いている） | 愛知県議会の議案ページのチャット |
| 管理画面にログインし、初回のパスワード変更ができる | admin のドメイン |
| 管理画面でサムネイルを上げて、公開サイトに表示される（Blob がつながっている） | 議案編集 → 公開サイト |
| （インタビューを出すなら）公開を許可して完了すると、しばらくして議案ページにトピックが出る | 議案ページの「トピック」 |
| 管理画面で議案を保存すると、公開サイトにすぐ反映される（`REVALIDATE_SECRET` が合っている） | 議案編集 → 公開サイト |
| 「市」「区町村」のリンクで「現在作成中」のページが出る | ヘッダー |

関係者だけで確かめるあいだは web に `BASIC_AUTH_USER`・`BASIC_AUTH_PASSWORD` を入れておき、公開するときに消して再デプロイします。

## 9. 2回目以降のデプロイ

- **CD を有効にしたあと:** main に入れるだけです。マイグレーション → デプロイの順に自動で行います。
- **CD を有効にする前:** 次の順に手で行います。
  1. スキーマを変えたときは、先に 2章のコマンドでマイグレーションを当てる
  2. Vercel で web・admin を再デプロイする（6.4）

マイグレーションは追加だけで書き、列を消すときは「コードから使うのをやめてデプロイ」→「次のリリースで列を消すマイグレーション」の2回に分けます（デプロイ中に古いコードが動いても壊れないように）。

## 10. 運用メモ

- **戻すとき:** Vercel の「Deployments」で戻したいデプロイの行の「⋯」→「Promote to Production」（または「Instant Rollback」）。DB は戻らないので、マイグレーションを含むリリースを戻すときは、そのマイグレーションが古いコードでも動くか確かめてからにします。Neon は「Backup & Restore」（左のメニュー）で時点を指定した復元ができます。
- **ログを見る:** Vercel のプロジェクトの「Logs」で、サーバー側のエラー（`console.error`）を見られます。DB の使用量は Neon の「Monitoring」、ファイルの容量は Vercel の Blob のストアの「Usage」。
- **ダミーを消す:** 議会に実データを入れると、ダミーは確認のうえで消えます。手で消すときは管理画面の議会設定の「ダミーデータを削除」。
- **AI の費用:** AI チャットは web の `CHAT_*_COST_LIMIT_USD` で上限を決めています。Gemini 側でも Google Cloud の予算アラートを設定しておきます（5章）。
- **Neon の容量:** AI インタビューの記録は期限を決めずに保存します（運用方針、2026-10-14）。容量は Neon の「Monitoring」で見て、無料枠（0.5GB 程度）に近づいたら有料プランにするか、AI チャットの記録など、インタビュー以外の古い記録を消すことを考えます。

## 11. まだ使っていないもの

- **本家の運営への連絡:** 設計 v3 10.2節のとおり、公開前に行います。

## 12. 付録: コマンドでの操作

1・5〜7章の画面の操作を、各サービスの CLI で行う方法です。どちらでやっても結果は同じで、途中から画面に切り替えても構いません。
2026年10月に Vercel CLI 60.1.3・neonctl 6.2.3・Google Cloud SDK 576・gh 2.97 の `--help` で確かめています。版によってオプションが変わることがあるので、違ったら `--help` を見てください。

秘密の値（接続 URL・キー・Deploy Hook の URL）は、コマンドの引数に書かず、`$(...)` で変数に入れるか標準入力で渡します（ターミナルの履歴に残さないため）。

### 12.0 CLI を入れてログインする

```bash
npm install -g vercel@60.1.3 neonctl@6.2.3   # gcloud と gh は Homebrew などで入れる
vercel login
neonctl auth
gcloud auth login
gh auth login
```

ログインは初回だけブラウザが開きます。Vercel のプロジェクト名は 12.3 の最初で変数に入れます。

### 12.1 Neon で DB を作る（1章）

```bash
neonctl projects create --name mirai-gikai-zenkoku --region-id aws-ap-southeast-1 --pg-version 17 --no-secrets --set-context
```

- `--region-id` で選べるのはこの版では米国・欧州・シンガポール（`aws-ap-southeast-1`）・シドニーなどで、東京はありません。Vercel の Function Region もシンガポール（`sin1`）に揃えます。
- `--set-context` で、以降の `neonctl` はこのプロジェクトを対象にします。`--no-secrets` で接続 URL を画面に出しません。

2〜4章（マイグレーション・初期データ・管理者）は、直接接続の URL を変数に入れてから、そのまま行います。

```bash
export DATABASE_URL="$(neonctl connection-string)"   # 直接接続（-pooler なし）
```

アプリ用の接続プールの URL は `neonctl connection-string --pooled` で出ます（12.3 で Vercel に入れる）。

### 12.2 Gemini の API キーを作る（5章）

Google Cloud のプロジェクトを使います（`<GCP プロジェクト ID>` は自分のもの）。

```bash
gcloud config set project <GCP プロジェクト ID>
gcloud billing projects link <GCP プロジェクト ID> --billing-account=<請求先アカウント ID>   # 課金がまだなら
gcloud services enable generativelanguage.googleapis.com apikeys.googleapis.com
gcloud services api-keys create --display-name=mirai-gikai-zenkoku --api-target=service=generativelanguage.googleapis.com
```

`--api-target` で、このキーで使える API を Gemini だけに絞っています。キーの文字列は次で取り出せます（12.3 で使う）。

```bash
KEY_NAME="$(gcloud services api-keys list --filter='displayName=mirai-gikai-zenkoku' --format='value(name)')"
export GEMINI_API_KEY="$(gcloud services api-keys get-key-string "$KEY_NAME" --format='value(keyString)')"
```

予算とアラートは `gcloud billing budgets create` でも作れますが、画面（5章の 4.）のほうが簡単です。

### 12.3 Vercel のプロジェクトを作る（6章）

6章の Vercel の操作を、次の ①〜⑧ の順にコマンドで行います。各項目の「画面なら」は、同じことを画面でやるときの場所です。途中まで画面で済ませてあれば、その項目は飛ばして構いません。

| | すること | 画面なら | 必須か |
|---|---|---|---|
| ① | プロジェクトを2つ作る | 6.1 の 1〜5 | 必須 |
| ② | 手元の `web/`・`admin/` をプロジェクトに結びつける | （画面には無い。コマンドで操作するための準備） | コマンドでやるなら必須 |
| ③ | ルートのフォルダ・フレームワーク・Node.js の版を設定する | 6.1 の表、Settings → Build and Deployment | 必須 |
| ④ | 関数を動かす地域を DB の近くにする | Settings → Functions | 任意（遠いと遅くなる） |
| ⑤ | GitHub のリポジトリとつなぐ | 6.1 の 2.（GitHub から Import すればつながる） | 必須 |
| ⑥ | 環境変数を入れる | 6.2 | 必須 |
| ⑦ | ファイルの置き場所（Blob）を admin につなぐ | 6.3 | 必須 |
| ⑧ | デプロイする（出し直す） | 6.4 の Redeploy | 必須 |
| （⑨） | 独自ドメインを付ける | Settings → Domains | 任意 |

> **画面でプロジェクトを作ってある場合（GitHub から Import した場合）:** ① と ⑤ は済んでいます。② から始め、③ は画面で設定済みなら確かめるだけ、⑥〜⑧ を行います。⑧ は画面の「Redeploy」でも構いません。

まず、プロジェクト名を変数に入れておきます。以下のコマンドはこの変数を使うので、名前が違っても書き換えはここだけです。画面で作ったプロジェクトの名前は、画面の左上か `vercel project ls` で確かめます。

```bash
WEB=mirai-gikai-zenkoku-web       # web のプロジェクト名
ADMIN=mirai-gikai-zenkoku-admin   # admin のプロジェクト名
```

**① プロジェクトを2つ作る**（画面で作ってあれば飛ばす）

```bash
vercel project add "$WEB"
vercel project add "$ADMIN"
```

**② 手元のフォルダをプロジェクトに結びつける**

`vercel` コマンドは、動かしたフォルダがどのプロジェクトかを `.vercel/` に覚えて、そのプロジェクトを操作します。`web/` を web のプロジェクトに、`admin/` を admin のプロジェクトに結びつけます（`.vercel/` は .gitignore 済み）。

```bash
(cd web && vercel link --project "$WEB" --yes)
(cd admin && vercel link --project "$ADMIN" --yes)
```

以降、`(cd web && vercel ...)` は web のプロジェクト、`(cd admin && vercel ...)` は admin のプロジェクトへの操作です。

**③ ルートのフォルダ・フレームワーク・Node.js の版を設定する**

このリポジトリは web と admin が別のフォルダにあるので、それぞれのプロジェクトに「どのフォルダをビルドするか」を教えます。画面で設定してあれば、`vercel project inspect "$WEB"` で確かめるだけで構いません。

```bash
vercel project update "$WEB" --root-directory web --framework nextjs --node-version 20.x --yes
vercel project update "$ADMIN" --root-directory admin --framework nextjs --node-version 20.x --yes
```

**④ 関数を動かす地域を DB の近くにする**（任意）

サーバー側の処理（DB を読むところ）が動く地域です。Neon の DB と同じ地域にすると速くなります。Neon がシンガポール（`aws-ap-southeast-1`）なら `sin1` です。`vercel project update` にはこの設定が無いので、Vercel の API を直接呼びます（`vercel api` はこの版では beta）。

```bash
vercel api "/v9/projects/$WEB" -X PATCH -f serverlessFunctionRegion=sin1
vercel api "/v9/projects/$ADMIN" -X PATCH -f serverlessFunctionRegion=sin1
```

**⑤ GitHub のリポジトリとつなぐ**（画面で GitHub から Import してあれば飛ばす）

```bash
(cd web && vercel git connect)
(cd admin && vercel git connect)
```

このリポジトリの GitHub の remote にプロジェクトをつなぎます。つなぐと、⑧ で GitHub の main のコードからビルドできるようになります。

**⑥ 環境変数を入れる**

手元の `.env.web.production`・`.env.admin.production`（.gitignore 済み。乱数の値を入れて手元で作ったもの）の `<...>` を実際の値に置き換えてから、1行ずつ流し込みます。値は標準入力で渡すので履歴に残りません。

```bash
(cd web && grep -E '^[A-Z_]+=.' ../.env.web.production | grep -v '=<' | while IFS='=' read -r k v; do printf '%s' "$v" | vercel env add "$k" production --sensitive --yes; done)
(cd admin && grep -E '^[A-Z_]+=.' ../.env.admin.production | grep -v '=<' | while IFS='=' read -r k v; do printf '%s' "$v" | vercel env add "$k" production --sensitive --yes; done)
```

- コメントの行と、`<...>` のまま残った行は飛ばします。流し込んだあとに `(cd web && vercel env ls)` で、足りないものが無いか確かめます。
- Neon の URL と Gemini のキーは、ファイルに書かずに直接入れることもできます（12.1・12.2 のあと）。

```bash
neonctl connection-string --pooled | (cd web && vercel env add DATABASE_URL production --sensitive --yes)
neonctl connection-string --pooled | (cd admin && vercel env add DATABASE_URL production --sensitive --yes)
printf '%s' "$GEMINI_API_KEY" | (cd web && vercel env add GOOGLE_GENERATIVE_AI_API_KEY production --sensitive --yes)
printf '%s' "$GEMINI_API_KEY" | (cd admin && vercel env add GOOGLE_GENERATIVE_AI_API_KEY production --sensitive --yes)
```

- すでにある変数を変えるときは `--force` を付けます。

**⑦ ファイルの置き場所（Blob）を admin につなぐ**

サムネイル画像などを置くストアを作り、admin のプロジェクトにつなぎます。つなぐと `BLOB_READ_WRITE_TOKEN` が admin に自動で入ります（web には要りません）。

```bash
(cd admin && vercel blob create-store mirai-gikai-zenkoku-files --access public --region sin1 --environment production --yes)
(cd admin && vercel env ls)   # BLOB_READ_WRITE_TOKEN があるか確かめる
```

リージョンに選べる値は Vercel のドキュメントの Regions の一覧を見てください。

**⑧ デプロイする（出し直す）**

環境変数は、入れたあとのデプロイから効きます。web・admin は `packages/` も使うので、手元からアップロードする `vercel deploy` ではなく、GitHub の main のコードからビルドさせます。そのために Deploy Hook（叩くとデプロイが始まる URL）を作ります。7章の CD でも同じものを使います。

```bash
vercel deploy-hooks create github-actions --project "$WEB" --ref main
vercel deploy-hooks create github-actions --project "$ADMIN" --ref main
```

表示された URL を控え（秘密として扱う）、`curl -X POST '<Deploy Hook の URL>'` でデプロイします。画面の「Redeploy」（6.4）でも構いません。進み具合は `(cd web && vercel ls)`、ビルドのログは `vercel inspect <デプロイの URL> --logs` で見られます。

**（⑨）独自ドメインを付ける**（任意。`*.vercel.app` のままなら不要）

```bash
vercel domains add gikai.example.jp "$WEB"
vercel domains add admin.gikai.example.jp "$ADMIN"
```

表示される DNS のレコードは、ドメインを管理している会社の側で登録します。付けたら `NEXT_PUBLIC_WEB_URL`・`ADMIN_URL` を新しいドメインに直して（⑥ の `--force`）、⑧ で出し直します。

### 12.4 GitHub Actions の CD を有効にする（7章）

順番に注意します。**環境と Secrets は、7章の4つのファイルを main にプッシュする前に作ります。** `deploy.yml` は main に入った時点ですぐ動くので、Secrets が無いとマイグレーションもデプロイも失敗します。Secrets に入れる Deploy Hook の URL は 12.3 の ⑧ で作ったものです。

| 順 | すること | いつ |
|---|---|---|
| 1 | 環境 `production` と Secrets 3つを作る（下のコマンド） | プッシュの前 |
| 2 | 7章の4つのファイルをコミットして main にプッシュする | |
| 3 | 自動で動いた「Migrate DB then Deploy」が緑になるか確かめる（`gh run watch`） | プッシュの後 |
| 4 | 手動で出し直したいときだけ `gh workflow run deploy.yml --ref main` | プッシュの後 |

プッシュする前に、12.3 までで Vercel 側を一度動く状態にしておきます（`vercel.json` を入れると Vercel が main から自分でビルドしなくなり、Deploy Hook からだけ出るようになるため。問題が起きたときに切り分けやすくなります）。

```bash
gh api -X PUT repos/Syogo-Suganoya/mirai-gikai-zenkoku/environments/production
URL="$(neonctl connection-string)"; [ -n "$URL" ] && printf '%s' "$URL" | gh secret set NEON_DATABASE_URL_UNPOOLED --env production || echo "接続 URL が取れませんでした（neonctl auth・12.1 の --set-context を確かめる）"
unset URL
gh secret set WEB_VERCEL_DEPLOY_HOOK_URL --env production     # 聞かれたら web の Deploy Hook の URL を貼る
gh secret set ADMIN_VERCEL_DEPLOY_HOOK_URL --env production   # admin の URL
gh secret list --env production
```

- `neonctl` が URL を出せない（ログインしていない・対象のプロジェクトが決まっていない）と、空の値が登録されてしまうので、上のように値があるときだけ登録します。Neon の画面で直接接続の URL をコピーして、`gh secret set NEON_DATABASE_URL_UNPOOLED --env production` を実行し、聞かれたら貼り付けても構いません。
- 承認者を付けるときは、`gh api -X PUT repos/<所有者>/<リポジトリ>/environments/production --input -` に `{"reviewers":[{"type":"User","id":<ユーザーの数値 ID>}]}` を渡します（画面のほうが簡単です）。
- 7章の4つのファイルを main にプッシュしたあと、手動で出し直すときは次のとおりです。

```bash
gh workflow run deploy.yml --ref main
gh run watch
```

### 12.5 終わったら

```bash
unset DATABASE_URL GEMINI_API_KEY
```

`.env.web.production`・`.env.admin.production` は、Vercel に入れ終わったらパスワード管理ツールに移して消すか、手元に置くなら他の人が読めない場所に置きます。
