## 1. 背景と方針

地方議会（都道府県・市区町村議会）版のみらい議会を作るプロジェクトが動いている。

**方針: 自治体ごとにフォークして作るのではなく、1つのプラットフォームで複数の議会を扱う。**
議案の概要さえ登録されれば、その議会のページは自動で出来上がる状態を目指す。

フォーク方式を採らない理由:

- 改修が各フォークに分かれて戻ってこなくなる（AIインタビュー・トピック分析などの改善が全自治体に行き渡らない）
- 自治体ごとにインフラ・運用者が必要になり、小さな自治体では維持できない
- 全国横断での比較・検索・オープンデータ化ができない

したがって作るべきものは「各地方のサイト」ではなく、**議案を登録する導線**と、**登録されたデータから議会ページを出す仕組み**である。

### 1.1 既存の地域版（fork方式）で実際に起きていること

有志による地域版（川崎市版 → 地方議会テンプレート `base-local/develop` → 福岡市版など）は、まさにフォーク方式で作られている。
`mirai-gikai-fukuoka-city` リポジトリを 2026-10-10 に比較した結果、上の懸念はすでに現実になっている。

| 観点 | 実測 |
|---|---|
| 分岐の大きさ | 共通の祖先（2026-03-20）以降、福岡市版だけのコミットが **210**、テンプレートだけのコミットが **283**。福岡市版の変更は 529 ファイル・約11万行 |
| 汎用機能の取り残し | 福岡市版で作られた **一般質問・委員会議事録・事務事業評価・市長記者会見・予算概要** の5機能は、どの議会にもある情報なのにテンプレートに入っていない。次に作る地域版はこれらが無い状態から始まる |
| 修正の届け方 | テンプレートの手順書が「merge すると毎回競合するので cherry-pick で取り込む」としている。修正1件を地域の数だけ手で運ぶ構造 |
| データの置き場所 | 委員会議事録の Markdown（142ファイル）や地域のシードデータがソースコードと一緒に git に入っている |
| 立ち上げの手間 | 地域ごとに fork、ブランチ名の置換、CI・ブランチ保護・デプロイの設定、ロゴ・配色・AGPLのリンク対応が要る。本家の fork を持っているアカウントは、同じ fork ネットワークの2つ目を作れない |

一方で、地域版の取り組みから得られた知見（2.9節の適合度調査、PDFの落とし穴、URLの再採番など）は本設計でそのまま使える。
地域版との関係は 4.1 節で扱う。

### 1.2 地域差をどこで吸収するか

地域ごとに違うものは4種類あり、**ソースコードを分ける必要があるものはない。**

| 層 | 地域差の例 | 吸収する場所 |
|---|---|---|
| 中身 | 議案・会派・会議録・AI解説 | DB（`assembly_id` で区別） |
| 機能の出し分け | インタビューを出すか、賛否をどの粒度で出すか、AIチャットの有無 | 議会ごとの設定（2.7節。管理画面から変更） |
| 取り込み | 議会サイトの構成・会議録システムの種類 | 取り込み元の登録（2.4節）と、業者ごとの読み取り |
| 見た目 | — | 1つのサービスなので議会ごとには変えない |

## 2. 論点

| # | 論点 | 結論（案） |
|---|---|---|
| 1 | 概要を誰がどう書くか | 人に要約を書かせない。議案書PDFを入れると AI が議案ごとに分割・下書きし、人は確認するだけにする。確認は注目議案に絞り、残りは「件名と原文へのリンク」で載せる |
| 2 | 国会専用のデータ構造をどうするか | `assemblies`（議会）を導入し、国会もその1件として扱う |
| 3 | 権限 | 全体管理者／確認者／編集者の3役割。確認者・編集者は担当議会だけ操作できる。小さな議会は確認者1人で回せる |
| 4 | 議案書・議事録をどう集めるか | 議会ごとに取り込み元（議案書・議決結果・参考資料・例規集・会議録など）のURLを登録し、新しく載ったものを自動で取り込む。住民からの投稿は受け付けない |
| 5 | 空のページ問題 | 全国の議会マスタを持ち、議案がない議会にも財政データ（全自治体共通の公開データ）を出す。議案がない議会は一覧に出さず、公開の通知の登録を呼びかける |
| 6 | 意見の届け先 | 最初はチームみらいの地方議員がいる議会に絞って始める |
| 7 | 専用の読み取り（スクレイピング） | **自治体ごとには作らない。会議録システムの業者ごとには作ってよい。** それ以外は一覧ページのリンクの差分を集め、中身はAIが読む |
| 8 | 議会ごとの機能の出し分け | コードではなく議会ごとの設定で切り替える。管理画面から変更できる |
| 9 | 中立性 | 確認者の名前と所属を明記し、異議申し立ての窓口と対応記録を公開する |
| 10 | どの議会から始めるか | 議会ごとに適合度調査を行い、議案の解説が作れるか（Tier）を確かめてから着手する |

### 2.1 概要を誰がどう書くか（最重要）

国会版では、運営が `bill_contents`（ふつう／くわしくの2段階）と `bills.knowledge_source`（AIチャット用の参照資料）を丁寧に作っている。
地方で同じことをボランティアに求めると続かない。また地方議会は次の事情がある。

- 定例会は年4回（3・6・9・12月）、会期は2〜4週間と短い
- 議案書の公開は開会の1週間前くらい。人手で書いていては採決までに間に合わない
- 1会期分の議案が1つのPDF（数十〜100ページ超）にまとまっていることが多い
- 人事案件・路線認定など、解説の必要性が低い議案も多い
- 中規模の市で1会期あたり20〜40件の議案がある。1件10〜15分で確認しても数時間かかり、これが年4回、担当者1〜2人に集中する

そこで登録の流れを次のようにする（アップロード画面・下書き確認画面）。

```
取り込み元に新しい議案書が載る → 自動で読み込む（1会期分まるごと）
  （取り込み元が未登録の議会・一覧に載らない議案書は、議案書PDFを手動でアップロード）
  → AI が議案ごとに分割（番号・正式名称・種類・ページ範囲）
  → AI が議案ごとに「確認の優先度」を付ける
  → 人が掲載のしかたを選ぶ（解説を付ける／件名と原文だけ載せる／載せない）
  → 解説を付ける議案だけ、AI が下書き（表示タイトル・ふつう・くわしく・knowledge_source）
  → 確認者が原文と並べて確認・修正 → 公開（is_review_completed = true）
```

#### 掲載の2段階

確認の手間を注目議案に集中させるため、公開のしかたを2段階に分ける。

| 掲載のしかた | 内容 | 向いている議案 |
|---|---|---|
| 解説あり | AIの下書きを確認者が確認した解説（ふつう／くわしく）を出す | 予算、新しい条例、住民生活に影響の大きい改正 |
| 件名と原文のみ | 件名・種類・付託委員会・議決結果と、原文へのリンクだけを出す | 人事案件、路線認定、軽微な改正など |

「件名と原文のみ」は確認者の確認なしで出してよい（議会の公開情報をそのまま並べるだけなので）。
後から「解説あり」に格上げできる。

#### 確認の優先度

AI は分割時に議案ごとの優先度（高・中・低）と理由を返す。ダッシュボード画面では優先度順に並べる。
目安は次のとおり。最終的に決めるのは確認者。

| 優先度 | 例 |
|---|---|
| 高 | 当初予算・大型の補正予算、新規条例、使用料・手数料・税の変更、住民の権利義務に関わる改正 |
| 中 | 上記以外の条例改正、契約・財産の取得 |
| 低 | 人事案件、路線認定、法令改正に伴う字句の整理 |

#### 解説の材料が足りない議案

地方議案の多くは「◯◯条例の一部を改正する条例」で、議案書には「第3条中『300円』を『400円』に改める」とだけ書かれていることが多い。
何がどう変わるかは、新旧対照表か例規集（現行の条例集）を見ないと分からない。補正予算も、議案書だけでは金額の内訳しか分からない。

- 取り込み元に **参考資料（新旧対照表・予算説明書）** と **例規集** を加える（2.4節）
- 改正条例の下書きでは、AI が例規集から現行の条文を引き、改正後の姿を組み立ててから解説する
- 会議録の提案理由説明に「その主な内容は」という節があれば、改正内容の材料になる（2.9節）
- 材料が議案書しかない議案は、下書き確認画面で「改正前後が確認できていない」と警告し、既定を「件名と原文のみ」にする

#### 品質の担保

- AI は下書きの各文について原文の根拠位置（資料・ページ・範囲）を返す。確認画面では原文側をハイライトする
- 数値・日付・金額が原文にない場合は警告を出す
- 公開できるのは確認者だけ。公開ページには「AIが下書きし、◯◯（所属）が確認（日付）」と明記する（2.8節）

### 2.2 データモデル

現状のテーブルは国会専用の前提になっている。

| 現状 | 地方で問題になる点 |
|---|---|
| `bills.originating_house: house_enum (HR/HC)` | 一院制なので不要 |
| `bill_status_enum`（introduced → in_originating_house → in_receiving_house → enacted/rejected） | 地方は 提出 → 委員会付託 → 本会議で可決・否決・継続審査 |
| `diet_sessions` | 地方では「令和8年9月定例会」「臨時会」の単位 |
| `mirai_stances` | チームみらいの議員がいない議会では出せない。また、議会の議決結果（会派ごとの賛否）とは別物 |
| `bills.shugiin_url` | 議会ごとに出典URLが異なる |

#### 議会マスタ

```sql
-- 議会マスタ（国会も1件として持つ）
create type assembly_type_enum as enum (
  'national', 'prefecture', 'city', 'special_ward', 'town', 'village'
);
create type assembly_status_enum as enum ('master_only', 'preparing', 'public');

create table assemblies (
  id uuid primary key default gen_random_uuid(),
  slug text not null unique,              -- 'national', 'aoba-city' など。URLに使う
  name text not null,                     -- 'あおば市議会'
  type assembly_type_enum not null,
  local_gov_code text unique,             -- 全国地方公共団体コード（国会は null）。財政データとの突合にも使う
  prefecture_code text,                   -- 都道府県での絞り込み用
  status assembly_status_enum not null default 'master_only',
  official_url text,
  has_mirai_member boolean not null default false, -- チームみらいの議員がいるか（事実）。表示するかは assembly_settings で決める
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
alter table assemblies enable row level security;

-- 会期・議案を議会に紐づける（既存データは national に寄せる）
alter table diet_sessions add column assembly_id uuid references assemblies(id);
alter table bills add column assembly_id uuid references assemblies(id);
```

#### 議案の地方用の項目

```sql
create type bill_publish_level_enum as enum ('title_only', 'explained');
create type bill_priority_enum as enum ('high', 'medium', 'low');

alter table bills add column bill_number text;      -- '議案第52号'
alter table bills add column official_name text;    -- 正式名称
alter table bills add column category text;         -- 予算／条例／人事・契約／請願・陳情／その他
alter table bills add column committee_name text;   -- 付託委員会
alter table bills add column source_url text;       -- 出典（shugiin_url の一般化）
alter table bills add column source_pages text;     -- 議案書中のページ範囲
alter table bills add column publish_level bill_publish_level_enum not null default 'explained'; -- 国会の既存データは explained
alter table bills add column review_priority bill_priority_enum; -- AIが付けた確認の優先度
alter table bills add column reviewed_by uuid references auth.users(id); -- 公開した確認者
alter table bills add column reviewed_at timestamptz;
alter table bills alter column originating_house drop not null;
```

`bill_status_enum` には地方用の値（`referred_to_committee`, `continued`, `withdrawn` など）を追加し、表示ラベルは議会の種類で切り替える。
`diet_sessions` は名前が国会寄りだが、リネームは影響範囲が大きいので当面そのまま使い、別途検討する。

#### 議決結果と会派ごとの賛否

議決結果は議会が公開する事実なので、チームみらいの議員の有無に関係なく出せる。
ただし公開の粒度が議会ごとに違う（地域版の調査では、同じ「議決結果」ページでも中身が4段階あった）。

| 粒度 | 例 |
|---|---|
| 議員別 | 議員ごとの賛否。議会だよりPDFの後ろのほうに載っていることが多い |
| 会派別 | 会派ごとの○×表。議案一覧PDFに同梱されていることがある |
| 票数のみ | 賛成◯・反対◯ |
| 可否のみ | 可決／否決 |

```sql
create type vote_granularity_enum as enum ('member', 'faction', 'count', 'result_only', 'unpublished');
create type bill_result_enum as enum ('passed', 'amended', 'rejected', 'continued', 'withdrawn', 'adopted', 'not_adopted');
create type faction_vote_enum as enum ('for', 'against', 'abstain', 'absent', 'split');

-- 会派（議会ごと。改選・再編があるので期間を持つ）
create table assembly_factions (
  id uuid primary key default gen_random_uuid(),
  assembly_id uuid not null references assemblies(id),
  name text not null,
  short_name text,
  seats smallint,
  valid_from date,
  valid_to date,
  created_at timestamptz not null default now()
);
alter table assembly_factions enable row level security;

-- 議決結果（議案ごとに1件）
create table bill_results (
  bill_id uuid primary key references bills(id),
  result bill_result_enum not null,
  decided_on date,
  yes_count smallint,
  no_count smallint,
  source_url text,                         -- 根拠の議決結果ページ
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
alter table bill_results enable row level security;

-- 会派ごとの賛否（粒度が faction 以上の議会だけ）
create table bill_faction_votes (
  bill_id uuid not null references bills(id),
  faction_id uuid not null references assembly_factions(id),
  vote faction_vote_enum not null,
  primary key (bill_id, faction_id)
);
alter table bill_faction_votes enable row level security;
```

議員別の賛否は、議員名簿の扱い（2.5節の Tier 0）とあわせてフェーズ4以降で検討する。

#### 議会ごとの設定

```sql
create table assembly_settings (
  assembly_id uuid primary key references assemblies(id),
  show_ai_chat boolean not null default true,
  show_interview boolean not null default false,     -- 届け先がある議会だけ true にする（2.6節）
  show_mirai_stance boolean not null default false,  -- has_mirai_member が true のときだけ有効にできる
  vote_granularity vote_granularity_enum not null default 'result_only',
  default_publish_level bill_publish_level_enum not null default 'title_only',
  updated_by uuid references auth.users(id),
  updated_at timestamptz not null default now()

alter table assembly_settings enable row level security;
```

項目をJSONにまとめず列で持つのは、型で検証でき、設定画面と公開側の表示条件を対応させやすいため。

#### 議案書の取り込み単位

```sql
create type import_source_enum as enum ('url', 'upload');
create type import_job_status_enum as enum (
  'splitting', 'waiting_selection', 'drafting', 'completed', 'failed'

create table bill_import_jobs (
  id uuid primary key default gen_random_uuid(),
```

### 2.3 権限

現状の admin は「Google Workspace のユーザーは自動で管理者」で、権限は全か無かの二択。
地方版ではチーム外のボランティアを招待するため、議会単位の役割を追加する（担当者管理画面）。

| 役割 | できること | 想定 |
|---|---|---|
| 全体管理者 | すべて。議会の追加、担当者の任命 | 運営（既存の admin ユーザー） |
| 確認者 | 担当議会の議案の登録・編集・**公開**、取り込み元の登録、議決結果の反映、議会の設定の変更、異議申し立てへの対応 | チームみらいの地方議員、地域リーダー、党外の有識者 |
| 編集者 | 担当議会の議案の登録・編集（公開不可） | サポーター |

- **小さな議会は確認者1人で全部できる。** 編集者と確認者の分業は小さな町には重いので、編集者がいなくても回るようにする
- 確認者には公開ページに出す **表示名と所属** を登録してもらう（2.8節）
- 党外の確認者（地域の有識者・他会派の議員など）も招待できる。役割は同じ

```sql
create type assembly_member_role_enum as enum ('reviewer', 'editor');
create table assembly_members (
  assembly_id uuid not null references assemblies(id),
  user_id uuid not null references auth.users(id),
  role assembly_member_role_enum not null,
  display_name text not null,               -- 公開ページに出す名前
  affiliation text not null,                -- 公開ページに出す所属（'◯◯市議会議員（チームみらい）' など）
  invited_by uuid,
  created_at timestamptz not null default now(),
  primary key (assembly_id, user_id)
);
alter table assembly_members enable row level security;
```

RLS ポリシーは定義せず（既存方針どおり）、認可は Server Actions / Loaders で `assembly_members` を見て判定する。

### 2.4 取り込み元の登録と自動取り込み

住民が議案書を投稿することはほぼ見込めないため、投稿の仕組みは作らない。
代わりに、議会ごとに取り込み元のURLを担当者が1度だけ登録し、新しく載ったものを自動で取り込む（取り込み元登録画面）。

#### 取り込み元の種類

都道府県議会の調査で、議会サイトの「議案の一覧」だけでは足りないことが分かった。取り込み元は次の種類を持つ。

| 種類 | 登録するページの例 | 取り込んだ後 | 優先 |
|---|---|---|---|
| 議案書 | 「定例会の一覧」「提出議案」など。**議会サイト以外（財政課など県庁・市役所側）のページも可** | 2.1節の流れ（分割 → 掲載のしかたを選ぶ → 下書き → 確認・公開） | 必須 |
| 議決結果 | 「議案等の審議結果」「提出議案と議決結果」など | 議決結果と会派ごとの賛否の候補を作る。確認者が反映する | 必須 |
| 参考資料 | 新旧対照表・予算説明書・議案参考資料 | 該当議案の下書きの材料にする | 推奨 |
| 例規集 | 現行の条例集（業者製のシステムが多い） | 改正条例の下書きで現行条文を引く | 推奨 |
| 日程 | 会期日程・委員会の付託表 | 会期の日程と付託委員会を埋める | 推奨 |
| 会議録（速報版） | 正式な会議録より先に出る速報版のページ | 委員会での質疑の要点を補う | 任意 |
| 会議録 | 会議録検索システム | 同上。AIチャットの参照資料に入れる | 任意 |

審議の進み具合の主な元は **議決結果** と **日程（付託表）** にする。
会議録は会議の2〜3か月後に公開されることが多く（徳島県議会は「定例会終了後おおむね3か月後」と明記）、審議の進み具合には間に合わない。
会議録は「後から委員会での質疑の要点を補い、議案詳細とAIチャットの資料を充実させる」用途に位置づける。

#### 読み取りの方式

| 方式 | 使う場面 | 仕組み |
|---|---|---|
| リンクの差分 | 議案書・議決結果・参考資料・日程など、自治体サイトの一覧ページ | 一覧ページのリンク（PDF・HTML）を毎回集め、前回との差分だけをAIに渡す。**「定例会の一覧 → 定例会ごとのページ → PDF」のように1〜2階層たどれる**ようにする |
| 業者ごとの読み取り | 会議録検索システム・例規集 | 検索フォーム形式で一覧ページを持たないため、システムの業者ごとに読み取りを作る |
| 手動アップロード | 一覧ページのない議会、紙でしか配られない議案書 | アップロード画面から登録する |

業者ごとの読み取りは、都道府県議会での採用数の多い順に作る。

| システム | 都道府県議会での採用数 | 備考 |
|---|---|---|
| `ssp.kaigiroku.net`（Discuss） | 19 | テナント型でURL構造が共通。画面はJavaScriptで描画されるため、静的取得では中身が取れない |
| `〜.dbsr.jp` | 13 | |
| `〜.gijiroku.com`（VOICES形式） | 6 | **会議録だけでなく議案・議決結果・会期日程のページも持つ**ので、議案側まで自動化しやすい |
| `kensakusystem.jp` | 3 | |

この4種類で都道府県議会47のうち41をカバーする。市区町村議会の採用状況は未調査（5章）。

#### 仕組み

- 確認の頻度は「会期中は毎日、閉会中は週1回」を既定にする（取り込み元ごとに変更可）
- AI が「どの種類の文書か／どの会期か／どの議案か」を判定する。関係ない文書は取り込まない
- 見つけたら担当者に通知し、ダッシュボード画面の通知欄に並べる
- 取得に失敗したら（サイトの引っ越し・ページの移動など）担当者に通知し、URLを直してもらう
- 登録時に「試しに読み込む」で、見つかるファイルとAIの判定を確認できるようにする

#### URLを文書の目印にしない

地域版の運用で、委員会議事録が **公開のたびに文書IDを振り直されて直リンクが壊れた** 実績がある。
同じURLで中身が差し替わることもある。そのため、文書の同一性はURLではなく **論理的な目印**（会期 × 種類 × 議案番号、会議録なら 開催日 × 会議名）で判定する。
URLは「最後に見つかった場所」として持つ。

#### PDFの取り込みで必ず出る落とし穴

規模の異なる自治体の議案一覧PDFで、次のすべてが出た。分割処理とAIへの指示に最初から織り込む。

- 件名が長いと2〜3行に折り返され、議案番号の行と分かれる。番号の行から次の番号までを1件として束ねる
- 議案番号の接頭辞が複数ある（議案第／報告第／認定第／諮問第／同意第／請願／陳情）。「報告」は議決されない
- 議決結果の表記ゆれ（可決／原案可決／認定／可決及び認定／原案適任／報告受理）。`bill_result_enum` への対応表を持つ
- 日付が全角数字のことがある（`９月１日`）
- 縦書きの表の見出し（会派名）は1文字ずつ分解されて抽出される。会派の並び順は確認者が一度対応づける
- 画像だけのPDFがある（議決結果PDFで2ページの抽出文字数が2文字という例があった）。この場合はOCRまたは画像として読めるAIに回す

#### 議会サイトへの配慮

- robots.txt で取得を拒否しているパスは取得しない。拒否されていたら取り込み元の登録時に警告する
- 同じサイトへの連続アクセスは間隔を空け、時間帯を分散する
- User-Agent にサービス名と連絡先を入れる
- 403 などで拒否されたら（長野県議会で確認）自動での再試行を止め、担当者に知らせる

#### データモデル

```sql
create type source_kind_enum as enum (
  'bills', 'results', 'references', 'reiki', 'schedule', 'minutes_flash', 'minutes'
);
create type fetch_method_enum as enum ('link_diff', 'vendor');
create type source_vendor_enum as enum ('discuss', 'dbsr', 'voices', 'kensakusystem');
create type check_interval_enum as enum ('session_daily', 'daily', 'weekly');
create type source_document_status_enum as enum ('detected', 'imported', 'ignored', 'failed');

-- 議会ごとの取り込み元（同じ種類を複数登録できる。議会サイトと県庁側の両方など）
create table assembly_sources (
  id uuid primary key default gen_random_uuid(),
  assembly_id uuid not null references assemblies(id),
  kind source_kind_enum not null,
  fetch_method fetch_method_enum not null default 'link_diff',
  vendor source_vendor_enum,                 -- fetch_method = vendor のとき
  vendor_tenant text,                        -- Discuss のテナント名など
  list_url text not null,                    -- 一覧ページ（または検索システムのトップ）のURL
  follow_depth smallint not null default 1,  -- 一覧ページから何階層たどるか（0〜2）
  check_interval check_interval_enum not null default 'session_daily',
  last_checked_at timestamptz,
  last_error text,                           -- 直近の取得失敗の内容（成功したら null）
  created_by uuid not null,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  unique (assembly_id, kind, list_url)
);
alter table assembly_sources enable row level security;

-- 取り込み元で見つけた文書（差分の判定と履歴に使う）
create table assembly_source_documents (
  id uuid primary key default gen_random_uuid(),
  source_id uuid not null references assembly_sources(id),
  url text not null,                         -- 最後に見つかった場所
  logical_key text,                          -- '令和8年9月定例会/議案書' など。URLが変わっても同じ文書と判定する目印
  content_hash text,                         -- 同じURLで中身が差し替わった場合の検知用
  ai_judgement jsonb,                        -- 種類・会期・議案番号など
  status source_document_status_enum not null,
  import_job_id uuid references bill_import_jobs(id),
  detected_at timestamptz not null default now(),
  unique (source_id, url)
);
create index on assembly_source_documents (source_id, logical_key);
alter table assembly_source_documents enable row level security;
```

v1 の `unique (assembly_id, kind)` は、議案書を議会サイトと県庁側の両方に置いている議会（長崎・福井・高知・徳島）で登録できなくなるため改めた。

### 2.5 空のページ問題

全国の議会（約1,800）をマスタとして一括投入するが、議案が登録されるのは一部に留まる。

- 「開会中の議会」一覧には公開議案がある議会だけを出す（議会選択画面）
- 公開議案がない議会のページは「まだ載っていません → 公開されたら知らせて」を出す（議案未掲載画面）
- 「公開されたら知らせて」の登録数を、次に取り組む議会を決める材料にする

#### 議案がなくても出せるもの（Tier 0）

総務省の「地方財政状況資料集」は **全自治体が共通の形式で公開している** ため、議会サイトの出来に関係なく、全国の自治体について財政の概要（歳入・歳出の内訳、人口あたりの額、財政指標）を出せる。
`assemblies.local_gov_code` で自治体と突き合わせる。地域版（福岡市版）で取得方法と検証のしかたが確立している。

- 議案未掲載画面にも財政の概要を出す。中身のあるページになるので noindex にしなくてよい
- 「この自治体の議会の議案が載ったら知らせて」の登録を、財政の概要の下に置く

議員・会派の名簿も多くの議会がHTMLで公開しているが、取り込みと更新（改選・会派の再編）の手間があるので、フェーズ4で扱う。

### 2.6 意見の届け先

国会版のAIインタビューは、集めた声を議員に届けることに価値がある。
受け取る議員がいない議会でインタビューを開くと「答えても意味がない」と感じさせてしまう。

- 最初はチームみらいの地方議員がいる3〜5議会に絞る
- インタビュー結果（レポート・トピック分析）は既存の仕組みをそのまま議会単位で使う
- 届け先がない議会では、インタビューは出さずAIチャットだけにする（`assembly_settings.show_interview`）
- 意見が少ないときのレポートは、件数が少ないことを明示する。複数の議案をまとめたレポートも選べるようにする

### 2.7 議会ごとの設定（議会設定画面）

機能の出し分けは、議会ごとの設定で行う。確認者が管理画面から変更できる。

| 設定 | 選択肢 | 既定 | 制約 |
|---|---|---|---|
| AIチャット | 出す／出さない | 出す | |
| AIインタビュー | 出す／出さない | 出さない | 届け先（議員）がいることを確認者が確認したときだけ出せる |
| チームみらいのスタンス | 出す／出さない | 出さない | `has_mirai_member` が true の議会だけ |
| 議決結果の粒度 | 議員別／会派別／票数のみ／可否のみ／非公開 | 可否のみ | 適合度調査（2.9節）の結果を初期値にする |
| 新しい議案の既定の掲載のしかた | 件名と原文のみ／解説あり | 件名と原文のみ | |

設計上の決まり:

- **データがない機能は出さない。** 設定がオンでも、対象のデータが0件なら公開側には出さない。設定画面には「データ0件のため非表示」と表示する
- **中立性に関わる表示は設定で消せない。** 「AIが下書きし、◯◯が確認」の表記、出典へのリンク、異議申し立ての窓口は常に出す
- 設定はキャッシュし、保存時に無効化する（全ページで読むため）
- 見た目（名称・ロゴ・配色）は議会ごとに変えない。1つのサービスとして統一する

### 2.8 中立性と透明性

党の議員が「中立な解説」を確認する構図は批判されやすい。賛否の欄を分けていても、「解説が党寄りだ」と言われたときの守りが弱い。

- 解説に **確認者の名前と所属** を明記する（`assembly_members.display_name` / `affiliation`）
- 議案詳細画面に **「解説に異議を申し立てる」** 窓口を置く。申し立てと対応（修正した／修正しない理由）の記録を公開する
- 党外の確認者（地域の有識者・他会派の議員など）も招待できる（2.3節）
- 解説とAIチャットのプロンプトには、国会版と同じ中立性のルール（特定の政党・会派・候補者を推奨しない、投票を呼びかけない）を入れる
- チームみらいのスタンスは、議会の議決結果とは別の欄に、党の見解であることを明示して出す

```sql
create type objection_status_enum as enum ('open', 'fixed', 'declined');
create table bill_objections (
  id uuid primary key default gen_random_uuid(),
  bill_id uuid not null references bills(id),
  body text not null,
  status objection_status_enum not null default 'open',
  response text,                            -- 対応内容（公開する）
  responded_by uuid references auth.users(id),
  created_at timestamptz not null default now(),
  responded_at timestamptz
);
alter table bill_objections enable row level security;
```

### 2.9 議会ごとの適合度調査

地方議会のサイトは、公開範囲も形式も自治体ごとにまったく違う。
議案が件名しか公開されていない、議決結果が可否のみ、会議録が要旨だけ、といった差があり、**仕組みを用意しても解説が作れない議会がある。**
そのため、議会を「準備中」にする前に適合度調査を行う。地域版で使われている調査手順（`council-survey`）の考え方を取り入れる。

#### 判定は3つを別々に出す

```
◯◯市議会：Tier N ／ 賛否 = <粒度> ／ アーカイブ = <強さ>
```

| Tier | 作れるもの | 成立条件 |
|---|---|---|
| Tier 0 | 財政の概要 | 無条件（2.5節） |
| Tier 1 | 議案一覧（件名・議決結果・会期） | 議案の一覧が何らかの形で公開されている |
| Tier 2 | 議案の解説 | 議案の内容を解説できる **厚み** の資料が取れる |

- Tier は累積。賛否の粒度とアーカイブ（会議録・委員会記録）の強さは Tier に含めず別に評価する
- Tier 2 は資料の有無ではなく **厚み** で判定する。条例改正の議案を3件選び（予算議案は厚く書かれがちなので選ばない）、「何がどう変わるか」が読み取れるかを見る
- 会議録の提案理由説明は2つの型がある。「その主な内容は」の節があれば改正内容が書かれている。地方自治法の条文の引用で締めて終わる型は件名以上の情報がない
- 障害の種類を分ける。**画像PDFなど読めない形式だが公開されているもの（OCRや工数で解決する）** と、**そもそも公開されていないもの（工数では解決しない）** を同じに扱わない
- すべての判定に根拠URLを付ける。確認できなかった項目は「なし」ではなく「未確認」とする

#### 調査結果の使い道

- Tier 2 に届く議会から「準備中」にする。Tier 1 の議会は「件名と原文のみ」で始める
- 調査で見つけたURLを、取り込み元（2.4節）と議会の設定（2.7節）の下書きにする
- 調査結果は履歴として残す（URLの安定性は2時点を比べないと判定できないため）

```sql
create table assembly_surveys (
  id uuid primary key default gen_random_uuid(),
  assembly_id uuid not null references assemblies(id),
  surveyed_at date not null,
  tier smallint not null check (tier between 0 and 2),
  vote_granularity vote_granularity_enum,
  archive_strength text,                    -- strong / medium / weak / none
  findings jsonb not null,                  -- 判定軸ごとの値と根拠URL
  report_markdown text,
  created_by uuid,
  created_at timestamptz not null default now()
);
alter table assembly_surveys enable row level security;
```

| 取り込み元登録画面 | 確認者 | 取り込み元の種類・URL・読み取りの方式・たどる階層・確認の頻度、試しに読み込む、取り込みの履歴、robots.txt の警告 |

| 担当者管理画面 | 全体管理者 | メール招待、議会ごとの役割、表示名と所属 |

## 4. 進め方

| フェーズ | 内容 | 公開への影響 |
|---|---|---|
| 0 | `assemblies` 導入、既存の会期・議案を国会に紐づけ、各クエリに議会の絞り込みを追加 | なし（国会版の見た目は変えない） |
| 1 | 試験議会（3〜5）の適合度調査。議会単位の権限（担当者管理画面）、議会設定画面、PDF一括登録とAI分割・優先度付け・下書き（アップロード画面・下書き確認画面）、掲載の2段階、ダッシュボード画面。議案書は手動アップロードで始め、議決結果は手入力。試験議会の担当者だけで運用 | 試験議会のみ限定公開 |
| 2 | 公開サイト（議会選択・議会トップ・議案詳細・議案未掲載の各画面）を正式公開。議決結果と会派ごとの賛否、確認者の明記、異議申し立て | 公開 |
| 3 | 取り込み元の登録と自動取り込み（リンクの差分。議案書・議決結果・参考資料・日程）。業者ごとの読み取りを採用数の多い順に（Discuss → dbsr → VOICES形式 → kensakusystem）。例規集の読み取り | 試験議会の負担を下げる |
| 4 | 議会マスタの全国投入、財政の概要（Tier 0）、公開通知、議員・会派の名簿。既存の地域版の機能（4.1節）の取り込み | 議会を広げる |

各フェーズの終わりに 6章の指標を確認し、続けるか・対策を先に入れるかを決める。

### 4.1 既存の地域版との関係

福岡市版などの地域版は、それぞれの運営者が独立して運用している。本設計はそれを置き換えることを前提にしない。

- **機能の取り込み**: 地域版で作られた一般質問・委員会議事録・市長記者会見・予算概要・事務事業評価は、どの議会にもある情報なので、フェーズ4以降に議会単位の機能として取り込む候補にする。取り込むときは地域版の運営者と相談する
- **知見の取り込み**: 適合度調査（2.9節）、PDFの落とし穴・URLの再採番（2.4節）、財政データの取得方法（2.5節）は本設計に反映済み
- **データの移行**: 地域版の運営者が希望する場合、その議会の議案・会派・議決結果を `assembly_id` 付きで取り込めるようにする（方法は未決）

## 6. 残るリスクと試験運用で測ること

v1 の懸念点のうち、確認作業の集中（6.1）・解説の材料不足（6.2）・議事録の遅さ（6.3）・検索システムの読み取り（6.4）・中立性の見え方（6.5）は、2章の設計に反映した。
残るのは、設計では解決できない次のリスク。

### 6.1 住民がそもそも来るか

- 地方議案の閲覧数は国会よりずっと少なく、インタビューが1議案あたり数件しか集まらない可能性がある
- 数件の意見で議員の判断材料になるかは疑問が残る。仕組みの問題ではなく集客の問題

対策案:

- 地域のSNS・LINE・議員本人の発信での告知を、立ち上げの手順（使い方ガイド）に組み込む
- 「公開されたら知らせて」の登録者に、会期ごとの注目議案（優先度が高の議案）を通知する
- 意見が少ないときのレポートの見せ方は 2.6節のとおり

### 6.2 確認者が続くか

掲載の2段階と優先度付けで負担は下がるが、年4回・会期前の1週間に確認が集中する構造は変わらない。
確認者が1人の議会では、その人が抜けると止まる。

対策案:

- 確認者が不在の会期は、自動で「件名と原文のみ」に切り替わるようにする（議会が止まって見えないようにする）
- 1議会に確認者を2人以上置くことを目標にする

### 6.3 試験運用で測ること

次の2つが成り立たなければ、ほかを作り込んでも回らない。試験運用（フェーズ1〜2）で必ず測る。

| 指標 | 見たいこと |
|---|---|
| 1会期あたりの確認時間（担当者1人あたり） | ボランティアで続けられる量か。優先度の付け方・掲載の2段階の線引きを見直す必要があるか |
| 1議案あたりの意見の数・閲覧数 | 議員の判断材料になる量が集まるか。6.1の対策が必要か |

あわせて次も記録し、自動化の範囲と優先度を決める材料にする。

| 指標 | 使い道 |
|---|---|
| 解説の修正量（AIの下書きからどれだけ直したか） | 下書きの品質。材料（参考資料・例規集）の追加の効果 |
| 「解説あり」と「件名と原文のみ」の比率 | 確認者の負担と、住民に届く情報量の釣り合い |
| 取り込み元から自動で取れた文書の割合 | フェーズ3の効果。業者ごとの読み取りを追加する順番 |
| 1会期あたりのAIコスト | 議会を広げたときの費用の見積もり |
| 異議申し立ての件数と内容 | 中立性の守りが機能しているか |
