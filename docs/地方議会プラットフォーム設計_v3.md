## 1. 背景と v2 からの変更点

v2 は「本家みらい議会に `assemblies` を入れ、国会も1議会として扱う」設計だった。
しかし本家の DB（Supabase）にはアクセスできないため、本家に組み込む形は取れない。
そこで **本家 develop のコードを出発点にした、独立した地方議会専用のプラットフォーム** として作る。

| 観点 | v2 | v3 |
|---|---|---|
| 置き場所 | 本家リポジトリ | 新規リポジトリ（GitHub の fork ではない） |
| 国会 | `assemblies` の1件として残す | 扱わない。国会専用の構造は地方用に置き換える |
| DB | 本家の Supabase | Neon（自前） |
| 認証・ファイル置き場 | Supabase Auth / Storage | メールとパスワードの自前ログイン / Cloudflare R2 |
| AI | 本家と同じ（Vercel AI Gateway 経由で OpenAI・Anthropic・Google を併用） | Gemini に統一 |
| URL | `/local/[assembly]/...` | `/[assembly]/...` |
| 議案の登録 | PDF → AI 分割・下書きが中心 | 上に加え、**単票の議案登録画面** と **CSV インポート** を最初から用意する |

v2 の方針「自治体ごとに fork せず、1つのプラットフォームで複数の議会を扱う」は変えない。
v3 で作るのは「本家の fork を1つ増やす」ことではなく、**地方議会をまとめて扱う1つのサービス** である。

## 2. リポジトリとインフラ

### 2.1 DB とリポジトリの作り方は関係ない

「本家の DB にアクセスできないから新規リポジトリにする」という理由づけは正確ではない。
ブランチ・fork・新規リポジトリのどれを選んでも、本家の DB は使えないので **DB は自前で用意する**（本プロジェクトでは Neon）。
リポジトリの作り方を決めるのは、DB ではなく次の2点である。

- 本家とは別のサービスとして運用し、別の場所にデプロイする（本家に PR を出す作業用の fork と混ぜない）
- 本家の改善をどう取り込むか

### 2.2 新規リポジトリ（履歴なし）で作る

GitHub の fork ではない新規リポジトリを作り、本家 develop のスナップショットを1コミット目にする。

```bash
# 1. 本家 develop の最新を取得し、基にした SHA を控える
git -C mirai-gikai fetch upstream develop
BASE_SHA=$(git -C mirai-gikai rev-parse upstream/develop)

# 2. 履歴なしで書き出す（.git を含まない）
mkdir mirai-gikai-local
git -C mirai-gikai archive "$BASE_SHA" | tar -x -C mirai-gikai-local

# 3. 新規リポジトリとして初回コミット
cd mirai-gikai-local
git init -b main
echo "$BASE_SHA" > UPSTREAM_BASE   # 取り込み元の SHA を記録
git add -A
git commit -m "chore: 本家 mirai-gikai develop ($BASE_SHA) を基に初期化"
gh repo create <org>/<repo> --public --source . --push
```

- **公開リポジトリにする**（AGPL-3.0 第13条。2.4節）
- 1コミット目の後、すぐに「リブランド」「国会専用部分の削除」を別コミットにする。本家との差分を読みやすくするため

### 2.3 本家の改善の取り込み

履歴がないので `git merge` はできない。取り込みは **差分をパッチとして当てる** 運用にする。

```bash
# 本家の clone で、前回取り込んだ SHA から最新までの差分を作る
PREV=$(cat ../mirai-gikai-local/UPSTREAM_BASE)
git fetch upstream develop
git diff "$PREV" upstream/develop -- web admin packages/shared packages/topic-analysis-core worker \
  > /tmp/upstream.patch

# 新リポジトリで当てる（当たらない部分は .rej に残る）
cd ../mirai-gikai-local
git apply --3way --reject /tmp/upstream.patch
git rev-parse upstream/develop > UPSTREAM_BASE   # 取り込んだら更新
```

- 取り込みの記録（日付・SHA・見送った変更と理由）を `UPSTREAM_SYNC.md` に残す
- 取り込みは定期的には行わず、**本家の更新に気づいたときに** 行う。地方に関係ない変更（国会専用の画面など）は見送る
- 差分が当たりにくい場所（3.2節の「改修」「置き換え」）は、本家の変更内容を読んで手で反映する

| 区分 | 対象 | 取り込みやすさ |
|---|---|---|
| そのまま使う | `packages/shared`（AI・プロンプト・ストリーム処理）、`packages/topic-analysis-core` の分析ロジック、UI 部品 `web/src/components` | パッチがほぼそのまま当たる |
| 改修する | bills・chat・interview 系の feature（議会の絞り込みを追加） | 部分的に手作業 |
| 置き換える | `packages/supabase`、各 feature の `repositories`、認証まわり、`supabase/` | 毎回手作業で読み替える（3.4節） |

### 2.4 ライセンスと名称（必須）

本家は AGPL-3.0 で、[FORK_GUIDELINES.md](../FORK_GUIDELINES.md) の追加条件がある。新規リポジトリでも本家のコードを使う以上、すべて守る。

- サービス名は **「みらい議会＠全国地方議会」** とする。ガイドラインの「みらい議会＠地域名」の形に合わせたもの。「全国地方議会」を地域名として扱ってよいかは、本家の運営への連絡（10章）のときに確認する
- チームみらいのロゴ・ヒーロー画像・OGP 画像・favicon を差し替える

### 3.4 DB: Neon と Supabase 依存の置き換え

#### 3.4.1 置き換えが必要なもの

Neon は Postgres そのもので、Supabase が持っている認証・ファイル置き場・クライアントライブラリはない。
本家 develop で Supabase に依存している箇所は次のとおり（2026-10-11 時点で計測）。

| 依存 | 規模 | 置き換え先 |
|---|---|---|
| Supabase クライアント（`createAdminClient` など） | 59 ファイル | Drizzle ORM + `@neondatabase/serverless` |
| DB function の呼び出し（`.rpc()`） | 12 ファイル。function の定義は 14 マイグレーション | function はそのまま Postgres に残し、Drizzle の `sql` で呼ぶ |
| Supabase Auth | 5 ファイル（admin の Google ログイン、web の匿名ユーザー）。`auth.users` への参照 7 箇所 | メールとパスワードの自前ログイン＋匿名 ID の Cookie（3.4.4節） |
| Supabase Storage | 1 ファイル（サムネイル） | Cloudflare R2 |
| 型の生成（`pnpm db:types:gen`） | | Drizzle のスキーマ定義から型を得る |

本家は Repository 層（[docs/repository-layer.md](../docs/repository-layer.md)）で DB アクセスを集めているので、**置き換えは各 feature の `repositories` と `packages/db` に閉じる**。
loaders・actions・services・UI は原則そのまま残し、本家からの取り込み（2.3節）で当たる範囲を広く保つ。

#### 3.4.2 `packages/db`

```
packages/db/
├── src/
│   ├── client.ts        # Neon への接続（サーバー専用）
│   ├── schema/          # Drizzle のテーブル定義（テーブルごとに1ファイル）
│   └── types.ts         # 行の型（InferSelectModel）。旧 Database["public"]["Tables"][...]["Row"] の代わり
├── migrations/          # drizzle-kit が出力する SQL
└── drizzle.config.ts
```

```ts
// packages/db/src/client.ts
import "server-only";
import { neon } from "@neondatabase/serverless";
import { drizzle } from "drizzle-orm/neon-http";
import * as schema from "./schema";

export function createDb() {
  return drizzle(neon(process.env.DATABASE_URL!), { schema });
}
```

- トランザクションが要る処理（CSV インポートの確定など）は `drizzle-orm/neon-serverless`（WebSocket）を使う
- 本家の Supabase の Row 型を参照している箇所は、`packages/db/src/types.ts` に同名の型を用意して import 先だけ差し替える

#### 3.4.3 マイグレーション

- 本家の `supabase/migrations`（108本）の結果を、**初期スキーマ1本** にまとめる
  - Supabase 固有のもの（`auth.users` への外部キー、`enable row level security`、`anon`・`authenticated` ロールへの grant、Storage のバケット定義）を取り除く
  - 国会専用の列・enum を消し（3.3節）、地方用のテーブル（5章）を加える
  - DB function 14本はそのまま移す。`tests/supabase/db-function` の統合テストも接続先を変えて流用する
- 以後のスキーマ変更は drizzle-kit（`drizzle-kit generate` → `drizzle-kit migrate`）で管理する
- RLS は使わない。認可は本家と同じくアプリ層（Server Actions / Loaders）で行う

#### 3.4.4 認証（メールとパスワード）

ログインは **メールアドレスとパスワードだけ** にする。認証ライブラリは使わず、移行元の `mirai-gikai-nagoya`（`lib/auth/admin.ts`、`db/migrations/002_create_admins.sql`）ですでに動いている方式を移す。

| 利用者 | 本家 | v3 |
|---|---|---|
| 管理者・確認者・編集者（admin） | Supabase Auth の Google ログイン。Google Workspace のユーザーは自動で管理者 | メールとパスワードでログイン。アカウントは全体管理者が担当者管理画面で作る。役割は `users.is_super_admin` と `assembly_members`（v2 2.3節） |
| 住民（web） | Supabase の匿名ユーザー（`signInAnonymously`） | ログインなし。初回アクセス時に匿名 ID を発行して Cookie に入れる |

```sql
create extension if not exists pgcrypto;

-- 管理画面のユーザー（全体管理者・確認者・編集者）
create table users (
  id uuid primary key default gen_random_uuid(),
  email text not null,
  password_hash text not null,              -- pgcrypto の crypt()（bcrypt）。照合も DB で行う
  is_super_admin boolean not null default false,
  must_change_password boolean not null default true,  -- 初回ログインでパスワードを変えさせる
  created_at timestamptz not null default now(),
  last_login_at timestamptz
);
create unique index users_email_key on users (lower(email));

-- ログイン中のセッション。Cookie にはランダムなトークン、DB にはその SHA-256 だけを保存する
create table user_sessions (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references users(id) on delete cascade,
  token_hash text not null unique,
  expires_at timestamptz not null,
  created_at timestamptz not null default now()
);
create index on user_sessions (expires_at);

-- 住民の匿名 ID（チャットのレート制限・インタビュー・リアクションの持ち主）
create table anonymous_visitors (
  id uuid primary key default gen_random_uuid(),
  created_at timestamptz not null default now(),
  last_seen_at timestamptz not null default now()
);
```

- **アカウントの作り方:** 全体管理者が担当者管理画面でメールアドレスと役割を入れると、初期パスワードが1度だけ表示される。全体管理者がそれを本人に渡し、本人は初回ログインで変更する。メール送信の仕組みは要らない。最初の全体管理者は CLI（移行元の `scripts/create-admin.ts` 相当）で作る
- **パスワードを忘れたとき:** 全体管理者が初期パスワードを発行し直す
- **守ること:** パスワードは12文字以上、ログイン失敗はメールアドレスと IP ごとに回数を制限する、Cookie は `HttpOnly`・`Secure`・`SameSite=Lax`、ログイン時にセッションを作り直す、期限切れのセッションは定期的に消す
- **住民の匿名 ID:** `anonymous_visitors.id` を署名付きの `HttpOnly` Cookie に入れる。本家で匿名ユーザーの ID（`auth.users.id`）を使っていた列（チャットのコスト集計、インタビューのセッション、リアクションなど）は `anonymous_visitors(id)` を参照する。本家の `use-anonymous-supabase-user.ts` と middleware のセッション更新は、この Cookie を発行・読み取る処理に置き換える
- AI チャットのレート制限・コスト上限（本家の仕組み）は、匿名 ID の取り方が変わるだけでそのまま使える
- 本家で管理画面のユーザー（`auth.users.id`）を参照していた列は `users(id)` を参照する
- 認可は本家と同じく Server Actions / Loaders で、`requireUser()`・`requireAssemblyRole(assemblyId, role)` のような関数を通して行う

#### 3.4.6 トレードオフ

- 本家の feature を取り込むとき、`repositories` と認証まわりは毎回 Drizzle・自前の認証に読み替える必要がある。本家に新しいテーブルが増えたら、そのたびに Drizzle のスキーマを書く
- 代わりに、Supabase の契約・ローカルの Supabase CLI（Docker 一式）が不要になり、Neon のブランチでプレビュー環境を安く作れる

## 4. AI（Gemini）

### 4.1 呼び出し方

本家は Vercel AI SDK（`ai`）を使い、モデルは Vercel AI Gateway 形式の ID（`google/gemini-3-flash` など）で [packages/shared/src/ai/models.ts](../packages/shared/src/ai/models.ts) に集めている。

v3 では **`@ai-sdk/google` で Gemini API を直接呼ぶ**。

- AI Gateway の契約・`AI_GATEWAY_API_KEY` が不要になり、`GOOGLE_GENERATIVE_AI_API_KEY` だけで動く
- 議案書PDFをファイルのまま Gemini に渡せる（v2 2.1節の分割・下書き、画像だけの PDF の読み取り）
- Vercel AI SDK の `generateText` / `streamText` / `generateObject` はそのまま使えるので、呼び出し側の変更はモデルの指定だけで済む

```ts
// packages/shared/src/ai/models.ts（v3）
import { google } from "@ai-sdk/google";

/** 用途ごとのモデル。呼び出し側は用途名で参照する */
export const AI_MODELS = {
  chat: "gemini-3.7-flash",
  interview: "gemini-3.7-flash",
  report: "gemini-3.7-pro",
  topicAnalysis: "gemini-3.7-pro",
  billSplit: "gemini-3.7-pro",   // 議案書PDFの分割・優先度付け
  billDraft: "gemini-3.7-pro",   // 解説の下書き
  moderation: "gemini-3.7-flash",
} as const;

  return google(AI_MODELS[purpose]);
}
```

- 本家で OpenAI・Anthropic のモデル（`gpt5_2`、`claude_sonnet_4_6` など）を指定している箇所は、すべて用途名に置き換える
- モデル名は Gemini の提供状況に合わせて変える。用途名で参照しているので変更は1ファイルで済む
- **使うのはその時点で最新の Gemini（3.5〜3.7 世代を想定）**。上の ID は例で、実際のモデル名と単価はフェーズ0の時点の Gemini API のドキュメントで確認する。速さが要る用途（チャット・インタビュー）は Flash、質が要る用途（レポート・分析・議案の下書き）は Pro を使う

### 4.2 コストの管理

- 本家のコスト上限（`CHAT_DAILY_USER_COST_LIMIT_USD` など）の仕組みは残し、単価表を Gemini のものに差し替える
- 議案書PDFの処理はトークン数が大きいので、議会ごと・会期ごとのコストを記録する（v2 6.3節の「1会期あたりの AI コスト」）
- 長い PDF を何度も読む処理（分割 → 議案ごとの下書き）は、Gemini のコンテキストキャッシュを使って同じ PDF の再読み込みを減らす

### 5.2 議案

## 6. 管理画面

画面の権限は v2 2.3節（全体管理者／確認者／編集者）に従う。確認者・編集者は担当議会のデータだけ扱える。

### 6.1 議案登録画面（1件ずつ）

本家の議案の作成・編集画面（`admin/src/features/bills-edit` の `bill-create-form.tsx`・`bill-form-fields.tsx`・`bill-contents-edit-form.tsx`）を拡張する。

| 区分 | 項目 |
|---|---|
| 基本 | 議会（担当議会から選択。1つだけなら固定）、会期、議案番号、正式名称、表示用タイトル、種類、提出者、提出日、付託委員会 |
| 審議 | 状態、状態の補足 |
| 出典 | 原文 URL、議案書 PDF（R2 にアップロード）、ページ範囲 |
| 掲載 | 掲載のしかた（件名と原文のみ／解説あり）、公開状態、注目 |
| 解説（解説ありのとき） | ふつう／くわしくの本文（本家の `bill-contents-edit-form` のまま）、AIチャットの参照資料 |
| AI 下書き | 「議案書から下書きを作る」ボタン。登録済みの PDF とページ範囲を Gemini に渡し、表示用タイトル・ふつう・くわしく・参照資料の下書きを入れる |
| 議決結果 | 結果・議決日・賛成数・反対数・会派ごとの賛否（議会設定の粒度に応じて項目を出す） |

- 「解説あり」で公開できるのは確認者だけ（v2 2.8節）。編集者は下書きの保存まで
- 議案番号は会期内で一意。重複したら保存前にエラーを出す
- 本家の「議案の複製」（`duplicate-bill`）は、同じ会期の似た議案を続けて入れるときに使えるので残す

### 6.2 CSV インポート画面

議会の立ち上げや、議会サイトが一覧表（Excel・CSV）で議案や議決結果を出している場合に、まとめて登録するための画面。

#### 6.2.1 対象

| 種類 | 使う人 | 主な用途 | 突き合わせの目印（自然キー） |
|---|---|---|---|
| 議会マスタ | 全体管理者 | 全国の議会の一括登録（約1,800件） | `local_gov_code` |
| 会派 | 確認者 | 改選・会派の再編のとき | 議会 × 会派名 × 有効開始日 |
| 会期 | 確認者 | 年度初めに1年分の定例会を入れる | 議会 × `session_key` |
| 議案 | 確認者・編集者 | 会期ごとの議案一覧 | 会期 × 議案番号 |
| 議決結果・会派ごとの賛否 | 確認者 | 閉会後の議決結果一覧表 | 会期 × 議案番号 |

目印が既にあれば **更新**、なければ **新規** にする。削除は CSV では行わない（画面から1件ずつ）。

#### 6.2.2 流れ

```
種類を選ぶ → テンプレート CSV をダウンロード（任意）
  → ファイルを選ぶ（ドラッグ＆ドロップ）
  → 文字コードを判定して読み込み、1行ずつ検証
  → 確認画面: 新規／更新／エラーの件数と行ごとの内容。更新は変更前後を並べる
  → エラーが0件なら「取り込む」で確定（1つのトランザクションで全行を反映）
  → 結果を履歴に残す（csv_import_jobs）
```

- エラーが1件でもあれば確定できない。エラーの行だけを CSV でダウンロードし、直して入れ直せるようにする
- 一度に扱う行数の上限は 5,000 行（議会マスタの全国分が入る大きさ）
- 確定前の内容はサーバーに保持し、確認画面と確定で同じものを使う（確定時に再アップロードさせない）
- 議案を CSV で入れたときは、議会設定の「新しい議案の既定の掲載のしかた」を使い、公開状態は下書きにする。公開は議案一覧から確認者が行う

#### 6.2.4 正規化（純粋関数）

CSV の読み込みと検証は外部依存のない純粋関数にし、`packages/shared/src/csv-import/` に置いてテストを書く（AGENTS.md の純粋関数の方針）。
本家の `packages/seed/csv/import-csv.ts` が使っている `csv-parse` を使う。

| 関数 | 内容 |
|---|---|
| `detectEncoding(bytes)` | UTF-8（BOM の有無）か Shift_JIS かを判定する。Excel で保存した CSV は Shift_JIS が多い |
| `parseCsv(text, kind)` | 見出しを列名に対応づけ、行の配列にする |
| `normalizeDate(value)` | 西暦・和暦（`R8.9.1`、`令和8年9月1日`）・全角数字を `YYYY-MM-DD` に |
| `normalizeBillNumber(value)` | 全角数字・空白のゆれを揃える（`議案第５２号` → `議案第52号`） |
| `normalizeBillResult(value)` | 表記ゆれを `bill_result_enum` に（下表） |
| `normalizeFactionVote(value)` | `○`・`〇`・`賛成` → `for` など |
| `validateRows(kind, rows, context)` | 必須・型・目印の重複・会期や会派の存在を確かめ、行ごとのエラーを返す |
| `diffRows(rows, existing)` | 新規／更新／変化なしに分ける |

議決結果の表記ゆれの対応表（v2 2.4節「PDF の取り込みで必ず出る落とし穴」より）:

| 表記 | 値 |
|---|---|
| 可決、原案可決、可決及び認定、認定、同意、原案適任、承認、知事の裁決書（案）を適当と認める | `passed` |
| 修正可決 | `amended` |
| 否決、不認定、不同意 | `rejected` |
| 継続審査、閉会中継続審査 | `continued` |
| 撤回 | `withdrawn` |
| 採択、一部採択 | `adopted` |
| 不採択 | `not_adopted` |
| 報告受理 | 取り込まない（報告は議決されない。警告を出す） |

### 7.1 ふりがな表示

移行元の「みらい議会＠愛知・名古屋」にあるふりがな表示を入れる。子どもや日本語を学んでいる人にも読めるようにするため。

- ヘッダーのスイッチで表示・非表示を切り替える（本家の「ふつう／くわしく」の切り替えと並べる）。選んだ状態は Cookie に残す
- ふりがなは **漢字の部分だけ** に振り、送り仮名には振らない（移行元と同じ）。`<ruby>` で表示する
- ふりがなは **保存するときにサーバーで作って DB に入れる**。表示のたびには作らない。対象は件名と解説の本文（ふつう／くわしく）
  - 議案登録画面（6.1節）・CSV インポート（6.2節）・AI の下書き・ダミーデータ（8.5節）のどれで保存しても作る
  - 作るのは形態素解析（kuromoji）。移行元の `lib/furigana` と `scripts/generate-explanation-furigana.ts` を `packages/shared/src/furigana/` に移し、テストを付ける
  - 固有名詞（地名・施設名）は読みを間違えやすいので、議案登録画面で件名のふりがなを手で直せるようにする
- AIチャットの回答にはふりがなを振らない（回答は流れてくる途中の文章なので、保存時に作る方式が使えない）

## 8. 初期データ（実データは愛知県議会のみ）

公開の時点で **実際の議案データを持つのは愛知県議会だけ** にする。
ほかの46都道府県議会には、画面の確認用に **ダミーデータ** を入れる（8.5節）。ダミーは、その議会の実データを CSV インポート（6.2節）や議案登録画面（6.1節）で入れるときに消す。
市区町村議会はダミーも入れず、議案0件で始める。議案のない議会は v2 2.5節どおり一覧に出さない。

### 8.1 移行元

同じリポジトリにある名古屋市会のデータは **移行しない**（今後も入れない）。

議会が愛知県だけだと、議会選択画面や都道府県からの絞り込み、議決結果の粒度による表示の違いが確かめられない。

#### 8.5.2 データでの目印

```sql
alter table sessions add column is_dummy boolean not null default false;
alter table bills add column is_dummy boolean not null default false;
alter table assembly_factions add column is_dummy boolean not null default false;
```

- 議決結果・会派ごとの賛否・解説は、議案の `is_dummy` に従う
- 議会（`assemblies`）そのものは実在するので目印を付けない。「この議会にダミーの議案があるか」は議案から求める
- 件名に「【ダミー】」を付けるのは、目印の列を見ない場所（スクリーンショット、SNS で共有されたリンクのプレビュー、AI の回答）でも分かるようにするため。列と件名の両方で示す

#### 8.5.3 画面と外部への出力での示し方

| 場所 | 示し方 |
|---|---|
| 議会トップ・議案詳細 | 画面上部に目立つ帯を出す: 「このページの議案は表示確認用のダミーです。実在の議案・議決結果ではありません」。議会の設定では消せない |
| 議案カード・議案一覧 | 件名の前に「ダミー」のバッジ。件名そのものにも「【ダミー】」 |
| 議会選択画面 | ダミーだけの議会に「ダミー」のバッジ。実データのある議会（愛知県）を先に並べる |
| OGP 画像・ページタイトル | 「【ダミー】」を付ける |
| 検索エンジン | `noindex`。サイトマップに載せない |
| オープンデータ | 出力しない |
| AI チャット | 使えるようにする（画面の確認のため）。システムプロンプトに「この議案は架空のもの」と入れ、回答の冒頭でそう伝えさせる |
| AI インタビュー・リアクション | 出さない（架空の議案に住民の意見を集めない） |
| 管理画面 | 一覧に「ダミー」のバッジと、ダミーだけ・実データだけの絞り込み |

#### 8.5.4 作り方と消し方

- **作り方:** `packages/seed/dummy/seed-dummy.ts` が、まだなければ46都道府県議会の議会マスタ（実在の情報なので `is_dummy` なし。ダミーを消しても残す）を作り、 8.5.1節の一覧とひな形から、46都道府県分（会期46・議案138・会派138）を `is_dummy = true` で直接入れる。CSV インポートは実データ専用にし、ダミーの目印を付ける手段を持たせない。ローカルの `pnpm seed` でも同じものが入る
- **消し方:** 管理画面の議会の画面に「ダミーデータを削除」ボタン（全体管理者のみ）。その議会の `is_dummy = true` の会期・議案と関連データをまとめて消す
- **実データを入れるとき:** ダミーが残っている議会に CSV インポートや議案登録画面で実データを入れようとしたら、「先にダミーを消しますか」と確認し、消してから取り込む。実データとダミーが同じ議会に並ばないようにする
- **本番にも入れる:** 公開サイトで全国の議会の画面を見せるため、ダミーは本番にも入れて公開する。実在の議案との区別は 8.5.3節の示し方で行う
